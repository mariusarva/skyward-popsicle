# 录屏（v84 起，v114 形态）

recovery 里没有 MediaCodec，也没有 ffmpeg，能用的只有 CPU。这一段因此全在
`crates/skyward-ui/src/record.rs` 里自己写：页面画布 → 块平均缩放 → BT.601 转
YUV420 → openh264 编 H.264 Baseline → 按采集时刻把 sample 装进 MP4。缩放与
编码都在后台线程，页面这一下只把画布抄走。

容器只有一种：**MP4**，码流 `avc1`（H.264 Baseline）。一段录屏一个文件，后缀 `.mp4`。

> 码流换过一次：v84–v107 装的是 MJPEG（`mp4v` + `esds`，objectTypeIndication
> `0x6C`），相册一律报「文件损坏」。v108 换成 H.264。
>
> 容器也换过几次：v94 / v95 整段 MP4，v96 改回 AVI，v100 加过第三档「AVI + MP4」
> 双写，v104 回到 AVI / MP4 两档，v106 把 AVI 整段删掉（`Avi` 结构、`idx1`、
> `Format` 枚举、录屏页第四行「格式」全部移除，`Container` 只剩 `Mp4`）。

## 为什么不是 MJPEG

这条链在 v106 的真机日志（`20261121-175928.zip`）里走到了死胡同，四步：

| 步 | 发生什么 |
|---|---|
| 1 | Android 的 `MPEG4Extractor` 用 `FourCC2MIME` 按 `stsd` 里的 fourcc 定 MIME。`mp4v` 被**硬映射**成 `MEDIA_MIMETYPE_VIDEO_MPEG4` —— 它**不看** `esds` 里的 objectTypeIndication，所以写 `0x6C`（JPEG）也没用 |
| 2 | 于是 `MediaCodec` 按 MPEG-4 Part 2 去创建 `c2.android.mpeg4.decoder`，喂进去的是 JPEG |
| 3 | 解第一帧就 `ERROR_MALFORMED`，相册把「解不出第一帧」直接显示成**文件损坏** |
| 4 | 文件其实是好的：那份日志是 `371 frames, 26940729 bytes in …mp4`，30 fps、12.4 秒、收尾正常。换容器写法也没用——系统里没有 MJPEG 解码器（`c2.android.mjpeg.decoder` 不存在，软解表里也没有） |

想被系统认，只能换码流。H.264 的 `avc1` + `avcC` 落在 `c2.android.avc.decoder`
上，Android 4.1 起每台设备都有（硬解或 Google 的软解），相册、ffmpeg、VLC 都直接放。

## 关于 MP4 剩下的两条实情

- **`moov` 写在文件末尾**：边录边写，索引得等每帧偏移定下来才能写。录制中途
  断电 / 拔电，那份 `.mp4` 打不开。这是「边录边写」的代价，换码流治不了。
- **上限 3.9 GB**：`stco` 是 32 位偏移，再大就得换 `co64`。

## 页面：录成什么样

录屏页第二条卡片是四行设置（容器那行只报 `MP4`，点它不换）：

| 项 | 档位 | 代码 |
|---|---|---|
| 分辨率 | 原画 1200×2608 / 高清 900×1956 / 标准 600×1304 / 流畅 450×978 | `SCALES = [(1,1),(3,4),(1,2),(3,8)]` 乘面板宽高，取偶 |
| 画质 | 高 `6.5 Mbps` / 中 `3.8 Mbps` / 低 `2.3 Mbps`（标准档 @30 帧） | `QUALITIES = [88,75,60]` → `Settings::bitrate()` |
| 帧率 | `60` / `30` / `24` / `15` | `RATES` |
| 容器 | `MP4`（里面 `H.264`） | `Container::ONLY`，没有别的 |

默认 **标准 + 中 + 30 帧**（`DEFAULT_SCALE/QUALITY/FPS`）。录制中四行锁定，
点一下只提示「正在录制，停下这一段才能改」——画面大小一变，编码器的
`SPS`/`PPS`、`stsd` 与已写出去的 `mdat` 都得重来。

画质不再是 JPEG 的 q 值，而是**目标码率**：像素 × 帧率 × bit 每像素（低 `0.10`、
中 `0.16`、高 `0.28`），夹在 `800 kbps … 48 Mbps`。录屏画面大半不动，H.264 靠
帧间预测能把静止部分压到几百字节，所以同一个观感下比 MJPEG 省得多。

| 档位 | 目标 | 每分钟 |
|---|---|---|
| 600×1304 · 中 · 30 fps | 3.8 Mbps | ≈ 28 MB |
| 600×1304 · 高 · 30 fps | 6.6 Mbps | ≈ 49 MB |
| 1200×2608 · 高 · 30 fps | 26.3 Mbps | ≈ 197 MB |

分辨率那行的副标题就是按这个算的：`600×1304 · 每分钟约 28 MB`（`Settings::per_frame()`）。

> 上表是目标值，不是真机实测。作为对照，MJPEG 那版在 600×1304 · q75 · 30 fps
> 上实测过 121 MB/min（48.3 s / 2896 帧 / 194,963,706 B），原画 1200×2608 是
> 304 MB/min。H.264 对同尺寸的目标只有它的四分之一左右。

## 计时胶囊

录制中屏幕右上角一枚 27 dp 高的胶囊，画在所有页面、卡片、控制中心之上
（`App::compose` 末尾、`out.dim` 之前，`compose_record_pill`）：

```
[ ● 0:42        已暂停 │ ▪ ]
  ↑点=暂停/继续          ↑点=结束这一段
  整枚可拖，拖到哪停在哪
```

| 项 | 值 |
|---|---|
| 高 / 圆角 | `27 dp` / `h/2` |
| 内边距 / 圆点 / 间距 | `11 dp` / `6.5 dp` / `8 dp` |
| 时间字号 | `13.5 dp`（`f.strong`，白） |
| 「已暂停」 | `11.5 dp`（`f.value`，白 alpha 150） |
| 底色 | `rgb(16,16,18)` alpha `226`（暂停时 `196`） |
| 红点 | `rgb(240,64,64)`；暂停时换成白色播放三角 |
| 分隔线 | `0.7 × 14 dp`，白 alpha 56 |
| 结束方块 | `dot × 1.45 = 9.4 dp` 圆角方块，白 alpha 232 |
| 默认位置 | `(m.w - margin - w, 46 dp)` |

三个命中矩形按**上一帧实际画出来的位置**认（`Pill { body, dot, stop }`），
存在 `App::record_pill`：

| 手指 | 判定 | 结果 |
|---|---|---|
| 按在整枚上挪 | 位移 > 4 dp | 胶囊停在松手处，贴边不越界；位置记进 `Record::pill`，下一段仍从这里开始 |
| 点左侧圆形 | 落在 `dot` 矩形 | 暂停 / 继续；胶囊上出现「已暂停」，录屏页状态行同步 |
| 点右侧方块 | 落在 `stop` 矩形（竖线到右端，约 30×27 dp） | 结束这一段，与录屏页「停止录制」同走 `Effect::RecordStop` → `Recorder::finish` |
| 点在时间文字上 | `moved == false && !dot && !stop` | 只震动，不做事 |

不录制时 `record_pill = None` —— 否则停下之后那块地方还会被当成胶囊吃掉手指。

## 暂停怎么算

- `Recorder::set_paused(on)` 先把 `AtomicBool` 置位：页面下一帧**连画布都不抄**
  （一帧 12 MB，暂停时抄了也是丢），同时给写线程发一条 `ctl`。
- 写线程收到「继续」时把 `last_at` 清成 `None`：下一帧按标称间隔
  （`90000/fps`）接上，暂停的那一段不进时间轴。所以文件里**既没有空档，
  也没有「停住 N 秒」**，只是少了一段。
- 已录时长同样不算暂停：`record.elapsed` 按 `(up_to - since - held)` 算，
  `up_to` 在暂停时取 `paused_at`、否则取当前时刻。
- 收尾时如果还停在暂停上（通道 `closed`），写线程直接 break —— 不会去等一帧
  它已经不会再写的画面，UI 线程也就不会卡在 `join` 上。

## 线程模型

| 阶段 | 谁做 | 细节 |
|---|---|---|
| 页面 | `Recorder::push(&Canvas)` | 先看 `ready` 与 `paused`；那一格**空着**才整块 `copy_from_slice` 抄进回收缓冲池（`POOL = 6`）再放进去（`Mutex<Option<Job>>` + `Condvar`），不空就丢这一张 —— 屏 120 Hz、编码 30，四分之三的 12.5 MB 抄写本来就会被顶掉；放进时撞上编码线程刚取走，`replace` 兜住，旧的还回池子，不排队 |
| 编码 | **1 条**（`record encode`） | 起来先编一帧预热（黑，丢掉）→ `ready`；之后自己按 `1/fps` 起表出帧，这一格没有新画面就再编一遍手里的 `Yuv420`；`shrink` 做块平均缩放（不插值，文字不糊）→ `to_i420` → openh264 |
| 写 | 1 条（`record mux`） | `recv_timeout(20ms)` 收到就写，间隔按**这一格的时间**算；不补帧、不重发 |
| 收尾 | 写线程 | 补 `mdat` 长度 → 写 `moov`（`avcC` 里的 SPS/PPS 由编码线程留在 `sets`） |

### 为什么只有一条编码线程

H.264 的 P 帧引的是**同一个编码器实例的上一帧**。两条线程各编各的、写线程再
按到达顺序混着写，解码器看到的就是两条互不相干的参考链 —— ffmpeg 报
`reference picture missing during reorder`，相册黑屏。MJPEG 一帧一张图，才可以
拆开并行；H.264 不行。

单实例在 600×1304 上有 30 帧/秒的余量（arm64 走纯 C++，见
`crates/skyward-ui/native/README.md`）。真跟不上也没关系：编码线程按这一格的
时间记 `at`，文件里是**更少的帧、更长的间隔**，时长照样对，画面也不花 —— 这
就是帧率行副标题那句「编码跟不上就少几帧，时长不变」。

### 定速出帧：编码线程自己起表

页面是跟着屏幕刷新率画的 —— 这块屏 120 Hz。v108 那年 `push` 每画一帧就抄一帧，
`settings.fps` 只进了 openh264 的 `fRcFps` 与 chunk 粒度，录出来是 67.7 fps。
v110 把它压在 `push` 里：

```rust
// v110：按 next += gap 放行，落后超过四格就从当下重新起算
fn due(&self) -> bool { … }
```

压住了「画得多快」，但没管「根本不画」：`Pages::show` 只在 `self.app.take_dirty()`
为真时 `compose` + `push`，录屏页静止时只有胶囊上的计时每秒跳一次、红点在闪。
v110 真机那份 44 秒的片子就是 762 帧：

| 项 | 设定 | 实际 |
|---|---|---|
| 帧率 | 30 fps | 762 帧 / 44.093 s = **17.28 fps** |
| 码率 | 3.8 Mbps | 11.5 MB / 44.09 s = **2.08 Mbps** |
| 停顿 | — | ≥ 66 ms 的 89 格占掉 **21.5 秒**，最长一格 883 ms |

所以 v112 把出帧从页面手里拿走了：页面只负责「最新的一帧是这张」，节奏归编码
线程。

```rust
// push：只放进最新一帧那一格，旧的一张还回池子
if let Some(old) = slot.replace(job)
    && let Ok(mut pool) = self.pool.lock()
    && pool.len() < POOL
{
    pool.push(old.rgba);
}
cvar.notify_one();
```

```rust
// 编码线程：自己起表，到点就编
let mut next = Instant::now();
loop {
    if let Some(job) = take(&mail) { …转成 yuv…; have = true; }
    let now = Instant::now();
    if now < next { wait_for(&mail, next - now); continue; }
    let at = if now.saturating_duration_since(next) <= gap / 2 { next } else { now };
    h264.encode(&yuv, 0, &mut out)?;
    done_tx.send((at, out[..len].to_vec(), key))?;
    next = at + gap;
}
```

`gap = 1s / fps`，`next` 是整格累加出来的：正常情况每一帧的 `at` 就是 `next`，
`stts` 里因此是干净的 `3000` tick。迟到的帧按实际发出时刻记，所以编码真跟不上
时是 `6000`、`9000` —— 时间长了对得上表，只是帧少。

这一格没有新画面时，编的是**同一份 `Yuv420`**：P 帧整帧 skip，几十字节到几 KB，
换来的是恒定帧率。注意是重编，不是把上一帧的字节重发一遍 —— 重发会让解码器的
参考链和 `stts` 对不上。

### 预热与第一帧的 IDR

两个坑一起解决：

| 现象 | 原因 | 改法 |
|---|---|---|
| 文件开头 638 ms + 474 ms 两个空洞（v108） | `H264::new` 与首帧编码在编码线程里同步做，那时还没有定速出帧：第一帧进去后几百毫秒没有帧，时间轴如实记下这段 | 编码线程先编一帧预热（不进文件）；`ready` 之前 `push` 直接返回，`stts` 从第一帧真实画面起算 |
| 加了预热之后第一帧变成 P 帧 | 预热帧占掉了初始化那次 IDR，P 帧里没有 SPS/PPS，`avcC` 会空 | 预热后 `ForceIntraFrame`，并在拿到 SPS/PPS 之前每帧都要一次 IDR |

`sky_h264_force_idr` 是 `h264_shim.cpp` 里新加的第四个函数，包的是
`ISVCEncoder::ForceIntraFrame(true, 0)`。

### 为什么要重编上一帧，而不是重发上一帧

v84 那份 849 MB 的录像（`Screenrecord_2026-11-21-10-45-57.avi`）逼出了 MJPEG
那套「只留最新帧、落后就挪时间轴、收尾不补」，因为补帧的成本只是重发一张
JPEG。H.264 不能重发：同一个 P 帧的字节再写一遍，它引的参考帧就变成了它自己，
解码器要么报 `reference picture missing during reorder`，要么整段花掉。

v112 补的是「没有新画面」这一格：把**同一份 `Yuv420` 再编一次**，编码器自己
产出一个合法的 P 帧（整帧 skip），参考链是接得上的。写线程始终「来多少写多少」，
不替编码器造帧。

v114 又把 `push` 收紧了一格：那一格**不空就直接丢**。屏 120 Hz、编码 30，四分之
三的 `copy_from_slice` 本来就会被下一张顶掉 —— 一帧十二兆，白抄三遍是每秒多占
一吉字节内存带宽，页面线程还得等它抄完。画面语义没变：每个编码格拿到的是「上
一格取走之后的第一张」，正好就是原来会被留在格子里的那张。

| 量到的（v84 那份） | 数 |
|---|---|
| 帧数 | `idx1` 5017 条，`avih.dwTotalFrames` 写着 5373（头里报的是时间轴） |
| 连续相同帧 | 1048 段，其中 **3550 帧（48.9 s → 167.2 s）是同一张不动的图** |
| 真正在变的 | 808 帧 |

## 容器

写线程手上就是 `Mp4` 一个出口，编码线程交来一帧就追一个 sample 进去：

```rust
pub enum Container { Mp4 }                 // 只有这一种
impl Container { pub const ONLY: Container = Container::Mp4; }
pub struct Take { file: File, path: PathBuf }
pub struct Summary { path: PathBuf, frames: u64, bytes: u64, millis: u64, dropped: u64 }
Recorder::start(take: Take, source, settings)
```

```
ftyp  24 B：isom / 0x0200 / isomiso2avc1mp41
mdat  一帧一个 sample：AVCC（4 字节大端长度 + NAL），直接贴着写；长度先写 0，收尾补
moov  mvhd + trak(tkhd + mdia(mdhd, hdlr, minf(vmhd, dinf, stbl(stsd, stss, stts, stsc, stsz, stco))))
```

| 项 | 值 |
|---|---|
| 码流标识 | `stsd` 里 `avc1`（78 字节 VisualSampleEntry）+ `avcC`：profile `0x42`（Baseline）、`lengthSizeMinusOne = 3`（AVCC 用 4 字节长度）、SPS / PPS 各一组 |
| SPS / PPS 从哪来 | 第一帧编完从编码器取（`sky_h264_parameter_sets`），剥掉 3/4 字节起始码，**只放进 `avcC`**，不写进 sample |
| 编码参数 | `CAMERA_VIDEO_REAL_TIME`、`RC_BITRATE_MODE`、`PRO_BASELINE`、CABAC 关（Baseline 只有 CAVLC）、`uiIntraPeriod = fps`（每秒一个 IDR）、单 slice、单线程 |
| 时基 | `mdhd` 90 kHz；60 / 30 / 24 / 15 都整除，标称每帧 `90000 / fps` |
| 帧间隔 | **按这一格的时间**算：`(at - prev_at) × 90000`，夹在 `1 … 90000×30`；正常是一格 `90000/fps`，连续相同的并成一条 `stts` 项 |
| 关键帧 | `stss` 记 1 起算的 IDR 序号；全是 IDR 时不写这个盒子 |
| chunk | 一秒一个；`stco` 只记每个 chunk 的第一个字节，`stsc` 两三条就把边界说完 |
| 收尾 | 补 `mdat` 长度，再整块写 `moov`（那时每帧偏移才定） |

### 一帧写一次

`MOST_BYTES` = 3.9 GB。到了这个上限写线程记一条
`record: the take is as big as its container allows; the frames after this are left out`，
之后的帧不再写，但**继续计数**（收尾那句日志里的 `frames left out`）。文件里
那一帧就是最后一帧 —— 收尾照常补索引，那份录像还开得开。

## 怎么验（不用上手机）

`scripts/check_record.py` 只读容器结构，不解码画面：

```sh
python scripts/check_record.py take.mp4
```

```
idle.mp4  1137541 B
  MP4：86 个 sample / 3 个 chunk / mdat 1136446 B / stts 共 273000 tick（3000×81 6000×5）/ avc1 + avcC（SPS 1 / PPS 1） / IDR 3 帧 / 文件 1137541 B
  ✓ 结构自洽
```

它查的是：

| 项 | 查什么 |
|---|---|
| 盒子 | 顶层就是 `ftyp` / `mdat` / `moov` 且首尾相接 |
| 长度 | `stsz` 合计 = `mdat` 身子 |
| 覆盖 | `stsc` + `stco` 走完正好盖住每个 sample |
| 码流 | `stsd` 是 `avc1`，`avcC` 里 SPS / PPS 都在、类型是 NAL 7 / 8 |
| 样本 | 每个 sample 都是「4 字节大端长度 + NAL」反复，正好走完 |
| 关键帧 | `stss` 记的正好是真 IDR 那几帧；没有 `stss` 时要求全片都是 IDR；第一帧必须是 IDR |
| 时间轴 | `stts` 合计 tick（除 90000 就是时长）与**格子分布**（括号里那个 `3000×81 6000×5`） |

`273000 tick` 换成时长 3.033 s，与 `Summary::millis` 对得上；格子分布里 81 格是
`3000` tick（33.3 ms，正是 30 帧）、5 格是 `6000`。**真机上该是一色 `3000`**；
这 5 格来自本机 e2e —— Windows 的 `Condvar` 等待精度是 15.6 ms，偶尔错过半格
就记成了两格（`at = now`），时长照样对。v60 那份 `still60.mp4` 是 `1500×151`：
格子短到 16.7 ms 时定时精度反而成了主角，但绝大部分仍是整格。

本机 e2e（`D:/WorkBuddyAI/tmp/recordcheck`，`#[path]` 引真的 `record.rs`）跑六个
场景：`busy`（120 Hz 推送）、`idle`（4 帧撒在 1.5 s、再空等 1 s）、`still30` /
`still60` / `still15`（没有新画面，靠重编上一帧出帧）、`paused`（暂停 1 s 再继续）。
最后那个验的是「暂停那段不进时间轴」：墙钟 2.73 s、文件 1.73 s，差的正是暂停的
1.00 s。

真机上量三件事：

| 看哪里 | 该是多少 |
|---|---|
| `record: stopped after N frames` 与 `s` | `N / s` ≈ 设置的帧率（30 档应 ≥ 28） |
| `check_record.py` 的格子分布 | 一色 `3000`；出现 `6000` 说明编码偶尔错过半格，多到占两成才是问题 |
| `MB/s` | 接近设置页的目标（30 帧 + 中档 ≈ 0.475 MB/s）；恒帧率下静止画面也照这个花 |

脚本里还留着 `check_avi`：v104 及更早那几份 `.avi` 里是 MJPEG，仍然可以拿它
验结构（`00dc` + SOI/EOI），新录的文件不会再出现这个容器。

## 日志

跑一段会看到四条（前两行是写线程收尾时打的，后两行是 UI 打的 —— 两处都报一
句「stopped after」，一条说时长与码率、一条说字节数与路径）：

```
record: started, 600×1304 · 3.8 Mbps · 30 fps · MP4 (H.264)
record: <N> frames, <M> MB in /sdcard/DCIM/Screenrecords/Screenrecord_<日期>-<时间>.mp4 · MP4 (H.264)
record: stopped after <N> frames, <秒> s, <M> MB, <MB/s> MB/s (<left out> frames left out, <P> pauses)
record: stopped after <N> frames, <字节> bytes in /sdcard/DCIM/Screenrecords/Screenrecord_<日期>-<时间>.mp4
```

不带暂停的一段只有 `record: started` 与收尾这几行；暂停 / 继续各打一条
`record: paused` / `record: carried on`。

| 字段 | 含义 | 健康值 |
|---|---|---|
| 第一行 `frames` / `MB` | 文件里到底写了多少帧、多大 | 与 `stsz` 的条数一致 |
| `s` | `stts` 摊出来的时长 | 与手上掐的表接近 |
| `MB/s` | 这一段平均码率 | 应接近设置页报的目标值（3.8 Mbps ≈ 0.475 MB/s）；文件里恒帧率，静止画面也按这个码率花 |
| `frames left out` | 到了 3.9 GB 上限之后没写的帧 | **应为 0** |
| `pauses` | 这一段按下暂停又继续了几次 | 与胶囊上按的对得上 |
