# 安装新系统

`crates/skyward-install/src/` 自己把 OTA 的 payload 解出来、直接写进将要启动的
那个槽，不建 COW、不需要合并。写不了的那种包（要改 super 布局、或者只带差量）
原样交给 `update_engine`，日志里说明是哪一条挡住了。

## 与 v40 的对比

| 项 | v40（2026-11-19 留档） | v97 |
|---|---|---|
| 写入 | 全部走 `update_engine`：单线程解 xz、建 COW、写完等合并 | v76 起自写 applier：`cores-1`（2–8）条线程解压后 `pwrite` 直写，**不建 COW** |
| 校验 | `update_engine` 逐块 | 按分区并行读回、SHA-256 比对 |
| 进度 | `update_engine` 的 `overall progress` | 自己按**字节**报，条不走回头路 |
| 实测 | 8.57 GB / 424 s = **20.7 MB/s**（v74，`update_engine` 路径） | 11.29 GB / 71 s = **162.0 MB/s**，读回 69.1 s = 167.3 MB/s（v84） |
| root | 合并后由管理器自己补 | 写回启动镜像前，用手机上的 `ksud` / `magiskboot` 原地重打，再读回比对 |
| 合并 | 必然要合并一次 | 直写的包**不用合并**，`set_next_slot` 之后直接能启动 |

v84 那两行日志值得留着对比：

```
install: 11.29 GB written in 71 s (162.0 MB/s), 58 partitions
install: the writing was read back in 69.1 s (167.3 MB/s)
```

写入 162 MB/s 已经贴着盘的上限（`dd iflag=direct` 实测 2.1 GB/s，但这里是
512 KB 一条随机写 + 现场解 xz）。校验那 69.1 秒与盘无关：单核 SHA-256 只有
约 170 MB/s，11.29 GB 正好 69 秒 —— 所以 v88 起校验改成按核并行。

## 两条路

```
install:
  Payload::open()                 # 从 sideload / FUSE / 本地文件读 CrAU 头
  applier::plan()  ── 说不行 ──→  `install: the payload is left to update_engine: <原因>`
        │ 说行
        ↓
  applier::write()                # 解压直写
  applier::check()                # 并行读回
  skyward_vab::set_next_slot()    # 让下一个槽启动
```

`direct` 是包在本机上的真实路径：`--payload=file:///sdcard/…` 直接读，不过 FUSE；
`adb sideload` 的包走 FUSE（块 1 MiB）。

## 门槛：写第一个字节之前就判掉

`applier::plan()` 把所有分区扫一遍、汇总成一句话，不是碰到第一处就退出：

| 情形 | 日志里的原因 |
|---|---|
| 块大小不是 4096 | `the payload measures its blocks in {n} bytes, and this recovery writes 4096` |
| 差量包（`partial_update`） | `the payload writes only what changed, and the rest of super as it is` |
| 有本程序不认识的 op | `the payload has operations this recovery does not apply: system (12 operations, kind 4); …`（按分区列出） |
| 某个 op 声称带数据却是空的 | `{name} has an operation of kind {k} that carries no data` |
| `super` 读不出来 | `super cannot be read for slot {B}: …` |
| 分区在 super 里被禁用 | `{name} is disabled in super for slot {B}` |
| 分区在包里和在 super 里不一样大 | `{name} takes {n} bytes in the package and {m} in super, so the layout would have to change` |
| 既不在 super 也不是本机的物理分区 | `{name} is in no super of slot {B} and in no partition of this phone` |
| 物理分区装不下 | `{name} takes {n} bytes in the package and the partition holds {m}` |
| op 写出来的长度与 `dst_length` 不符 | `{name} writes {n} bytes into {m}` |
| 单个 op 超过 512 MiB 上限 | `an operation writes {n} bytes, past the 536870912 this holds` |

真机上的官方完整包（5820 个 op）：`REPLACE` 565 / `REPLACE_BZ` 231 /
`REPLACE_XZ` 5024，没有 `MOVE` / `BSDIFF` / `ZERO` / `DISCARD` —— 全部走直写。

## payload 头与 manifest

| 项 | 值 |
|---|---|
| 头 | `CrAU` + `>Q version` + `>Q manifest_size` + `>I sig_size` |
| manifest | protobuf：`block_size` field 3、`partitions` 13、`dynamic_partition_metadata` 15、`partial_update` 16 |
| op 的 hash | field **8**（field 7 是 `dst_length`，别认错） |
| 数据 | `data_offset` 相对 payload 起点；`REPLACE_XZ` 用 `liblzma`（static），`REPLACE_BZ` 用 `bzip2 0.6.1` 的纯 Rust `MultiBzDecoder` |

`liblzma` 用 static 链接，不要用 `xz2` —— 它会撞 `links = "lzma"`。

## super 的布局（liblp）

| 项 | 位置 / 大小 |
|---|---|
| geometry（两份） | `4096` 起，各 `4096` B |
| 主 metadata（slot N） | `12288 + metadata_max_size × N` |
| 备 metadata（slot N） | 主 + `metadata_max_size × metadata_slot_count` |
| 头 | v1.0/v1.1 到 `flags` 之前；v1.2 为 **256 B** |
| 表 | 从 `slot_start + header_size` 开始 |
| 分区名 | 36 字节内联 |
| extent | packed 24 字节 |

分区名匹配顺序：`name` → `name + _b`（这一槽的后缀）→ 去掉 `_a` / `_b`。
B 槽的 metadata 里名字带 `_b`，原厂的可能不带；另外还有 `odm_b-cow` 这种
`attrs = 0` 的影子分区，**不能**把 `-cow` 误认成目标分区。

## 写入

- 任务单位是 `(分区, stretch)`：一个分区的逻辑区段可能跨多个 extent，每条各自
  一个任务，谁空谁拿。
- 一条读线程按顺序读 payload 并给进度计数（通道 `AHEAD = 8`）；解压写盘的是
  `cores - 1`，`clamp(2, 8)` —— 这台机器上是 **7** 条。每条约 28 MB/s，盘还有
  大量余量，所以加密解压是瓶颈。
- 解出来的数据直接 `pwrite` 到 `span.device + at`：不建 COW，写完这个槽就是
  完整的，**不需要合并**。
- 写的过程中不吃 `osync`，收尾 `sync` 一次。

## 进度

| 阶段 | 报什么 |
|---|---|
| 开始 | `install: 58 partitions, 11.29 GB, written straight into slot B as it is read` |
| Writing | `Stage::Writing { done, total }`，按字节，`total` 是计划的总字节 |
| 写完 | `install: 11.29 GB written in 71 s (162.0 MB/s), 58 partitions` |
| Verifying | `Stage::Verifying { index, count, partition, done, total }`，仍按字节 |
| 收尾 | `Stage::Finishing` → 写回 → 可重启 |

校验阶段报给页面的分寸：**每 4 MB** 一条消息、**100 ms** 至多一次、分区名
**700 ms** 才换一次（八条线程同时换分区时名字一刻一变反而读不出来）。
`total = 0` 表示来源不说字节数（走 `update_engine` 的那条路就是 0），页面退回
按分区个数算。

`odm` 一个分区占 58 分之一却要读 21.5 秒、`product` 29.2 秒 —— 这就是 v84
页面上「条一动不动」的那 50 秒；改成按字节之后条一直在走。

## 校验：按分区并行

```
workers = cores.clamp(2, 8)          # 这台机器 8 条
每分区一条 SHA-256，读完把 read 计数丢给 UI 线程
```

| 项 | 值 |
|---|---|
| 读块 | 1 MiB（`CHUNK`） |
| 报进度 | 每 4 MiB 一条 |
| 洞 | 按零计入哈希（系统看到的也是零） |
| 失败 | 记第一条错误、置 `stop`，其余线程退出 |
| 逐分区日志 | `install: {name} read back and matched its hash` |
| 汇总日志 | `install: the writing was read back in {n} s ({m} MB/s)` |

单核 SHA-256 约 170 MB/s，盘 1.4 GB/s，所以八条并行理论上把 69 秒压到十几秒。
**这一版（v88 起）还没有真机数据**，验收看 `the writing was read back in` 的秒数。

## 回退到 update_engine 时

| 项 | 行为 |
|---|---|
| 解压线程 | `update_engine` 自己决定，读 `ro.virtual_ab.num_worker_threads`；`--max_threads` 参数在这一版**不存在** |
| 日志 | 收尾把最后 4 MB 抄到 `/mnt/vendor/persist/update_engine.log`（`/skyward` 是内存盘，重启就没了） |
| 频率 | `skyward_sys::cpu::demand()` 把 cluster 顶到最高频，直到结束 |
| 预读 | 同时放宽 |

## 写完以后，在同一个会话里做完的事

1. **定槽**：`skyward_vab::set_next_slot(next)`，日志 `install: slot B starts next, and nothing waits to be merged`。
2. **回写 recovery 自己**：`root::keep` 打**更新写的那张**镜像 → `root::carry` 整分区搬运 → `put_back` 写回。块设备的 `st_size` 是 0，分区大小必须走 `BLKGETSIZE64`；写回启动分区前补零到分区大小（旧 AVB footer 会让它开不了机）。
3. **root**：`ksud boot-patch -o` 的参数要**文件夹**（给文件名会 `write out new boot failed`，一个字节都不写）；Magisk 的 `boot_patch.sh` 只读 `$1`；recovery 的 `getprop` 答不出 SDK / ABI，得先写替身顶在 `PATH` 前。
4. **vbmeta**：`avbctl.rs` 备份到 `/sdcard/Skyward/vbmeta/vbmeta_<槽>-r<回滚>-<unix秒>.img`（`AVB0` magic + 头里的 `length()`），写回前整份核对；回滚索引低于当前槽就拒。
5. **合并**（只对 COW 包）：`snapshots::initiate` 第一行 `ensure!(dm::status)`；`merge::run` 在 `start_merge` 之前先 `map_snapshots(slot)`。`MergeStatus`：0/1/2/3 进行中、4 `NeedsReboot`、5 `Completed`、6 `Cancelled`；`MergeCompleted` 不能映射成 `None`。boot control 拿不到就写 misc offset `4060`。

一个未合并的 snapshot = 进不了系统 = 看起来像无限重启：`begin()` 先
`open_metadata()`；`resume_merge` 对 `Installed` / `Waiting` / `Merging` / `Failed`
一律 `start_merge`。

## 两个只在真机上才出现的错

| 错 | 真因 |
|---|---|
| 离开已装系统时 `EBUSY` | 还有进程开着那个分区；`pin` 遍历所有进程的 maps 与 fd，遇 `EBUSY` 走 `MNT_DETACH` |
| 写分区 `EPERM` | 不是权限，是分区还是只读：先 `BLKROSET` 清 ro；仍 `EPERM` 就按 `start × 512` 从父盘偏移写，写前逐字节比对 |

## 页面上的三个阶段

| 页面 | 第 1 步 | 第 2 步 | 第 3 步 |
|---|---|---|---|
| 安装 | 读包、校验签名 | 写入（条按字节） | 读回校验（条按字节，分区名慢换） |
| 合并 | 映射快照 | 合并（`MergeStatus`） | 可以重启 |
| root | 取回启动镜像 | 重打 | 写回、读回比对 |
